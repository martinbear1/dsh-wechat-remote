# 微信身份认证方案 · 设计讨论 v1

> 本文档是「dsh-wechat-remote」插件认证层的设计讨论记录：微信身份体系的事实与限制、
> 安全对比、推荐架构、待决策点。实现前先定案本文档。

## 1. 目标

微信小程序（`E:\Deepseek Harness`，已实现局域网控制）与 Windows 上的 DSH 之间的
**连接、权鉴与安全身份认证**，作为一个全新的、官方规范适配的独立插件实现：

- 电脑端插件：一条命令安装（`dsh plugin --profile web add …`），进程内运行；
- 身份：**微信用户 openid 一对一绑定**这台电脑的 DSH；
- 使用：扫一扫即配对、即绑定、即登录（目标体验）；
- 公网：预留接口字段，暂不暴露。

## 2. 微信身份体系：事实与限制（调研结论）

### 2.1 能拿到的身份

| 标识 | 获取方式 | 说明 |
|---|---|---|
| **openid** | `wx.login()` → jsCode → 服务端 `code2session`（appid+secret） | 用户在小程序内的唯一假名 ID；**同一个小程序内永久稳定**；个人主体可用 ✅（本方案的身份基石） |
| unionid | 同一开放平台账号绑定多个应用后，`code2session` 附带 | 跨小程序/公众号统一身份；个人项目无开放平台账号，跳过 |
| 昵称/头像 | 头像昵称填写组件（用户主动点选） | 需要用户显式操作，不能静默获取；本方案不需要 |

### 2.2 拿不到的（必须纠正预期）

- **微信号 / 微信ID：任何接口都拿不到**。微信出于隐私设计从不向小程序暴露用户的微信号，
  开放平台也拿不到。所谓"用微信ID做身份"只能落到 **openid**（openid 就是微信给你的
  身份识别码，只是不是用户可见的微信号）。
- **手机号**：`getPhoneNumber` 要求非个人主体 + 每次调用付费（0.03 元/次），个人小程序
  直接不可用，也不建议作为身份主键。

### 2.3 登录会话的规则

- `wx.login()` 返回的 jsCode：**一次性、5 分钟有效**；用一次即作废，必须服务端即时兑换。
- `code2session` 必须在**服务端**调用（appid+secret 不能进小程序代码）。本方案里
  "服务端"就是装在用户自己电脑上的插件 —— 天然合适，无需任何云端服务器。
- `session_key` 由服务端持有；本方案不需要解密任何加密数据，**无需保存 session_key**。

### 2.4 「扫一扫直接进小程序」的规则（关键限制）

- **普通二维码（我们自己生成的载荷）用微信扫一扫，不会打开任何小程序**——微信只会显示
  文本/链接。能让微信扫码跳进小程序的只有三类官方产物：
  1. **小程序码**（`wxacode.getUnlimited`）：`scene` 参数 ≤32 字符（放配对码绰绰有余）、
     永久有效、数量无上限；**但正式扫码进入要求小程序已发布**（开发期体验版需用编译模式
     注入 scene 测试）；每次配对生成一张 = 一次 API 调用（有频率配额，但配对是低频事件，够用）。
  2. **URL Link / URL Scheme**：同样要求小程序已发布，且各有生成配额（个人主体是否可用
     需以你小程序的账号资格为准）。
- 结论：**"扫电脑上的码直接进小程序"（扫一扫直达）是发布后的增强能力，开发期与个人使用
  阶段以"先打开小程序 → 点扫码 → 小程序读二维码"为主路径**（见 §4.2 方案 A/B）。

### 2.5 网络规则（对公网预留的影响）

- 真机开发期：局域网 `http://192.168.x.x:3092` 可行（开发者工具关闭域名校验即可）。
- 小程序**发布版**：`wx.request` / `wx.connectSocket` 必须走**已备案域名的 HTTPS**
  —— 局域网明文 http 在正式版不可用。所以"公网通道"未来的现实形态是：备案 HTTPS 域名
  反代到本机（或 Tailscale Funnel 之类提供 HTTPS 的通道 + 在小程序后台配置合法域名）。

## 3. 安全分析：微信身份 vs 纯 token

### 3.1 旧 iOS 方案（对照组）

长期 Bearer token（256 位随机）：**持有即全权**——谁拿到字符串谁就能控制 DSH；
无身份概念、无法按人撤销、可在多设备间随意复制。

### 3.2 微信 openid 绑定方案

```
配对： 屏幕秘密(一次性配对码) + wx.login jsCode
       → PC 端 code2session 解析 openid
       → 持久化 { openid → token } 绑定
启动： wx.login 新 jsCode → /pair/verify-wechat 复核 openid 匹配 → 发放（可滚动）token
```

### 3.3 更安全吗？——是，但有边界

**更强的点：**

1. **身份绑定**：token 不再是无主的字符串；服务端知道"这是哪个微信用户"。
2. **启动复核**：每次启动都要用当前微信登录态换新凭证 —— 偷走存储里的 token 只能用到
   它过期，攻击者还必须同时控制被绑定的微信账号。
3. **按人撤销**：解绑/踢出某一个 openid，不影响其他。
4. **凭证滚动**（可选）：每次复核成功即轮换 token，旧凭证立即作废 —— 泄露窗口 = 一次
   会话周期。

**边界（诚实说明）：**

- openid 是**假名**，不是实名 —— 身份强度 = "这个微信账号能登录"，不是"这个人是张三"。
- 微信账号本身被盗/被借，绑定随之失守（与一切 OAuth 同理）。
- 电脑上要存小程序的 **appid+secret**（`~/.dsh/gate-wechat.json`，0600）：泄露后攻击者
  能解析 jsCode 换 openid，但**无法伪造绑定**（绑定还需要屏幕上的配对码），风险可控。

### 3.4 结论

微信 openid 绑定**明显强于**纯 token（身份 + 复核 + 可撤销），且对用户**零额外成本**
（不用记密码、不用填任何东西）。token 层保留作为传输层凭证（防御纵深），身份层由微信提供。

## 4. 推荐架构

### 4.1 插件形态（完全沿用已验证的官方范式）

单包三角色，与 iOS 插件同构：

- `cordis.patch.yml`：`- insert: - id: gate, name: '@harness-remote/dsh-wechat-remote'`
- 宿主插件（lib/index.js）：进程内网关，两个门（**已拍板端口，见 §5b**）：
  - 本地门 `127.0.0.1:3093`：`GET /pair`（电脑端配对页+二维码）、`GET /pair/code`
    （官方 Web UI 侧边栏按钮）、`GET /gate/status`
  - 公网门 `0.0.0.0:3092`：除 `POST /pair/claim-wechat` 外全部要求 Bearer；验过即反代
    到 `127.0.0.1:3080`（Host 重写走官方栅栏合法通道）
- 客户端插件（lib/client.js）：侧边栏「微信连接」配对按钮（注册官方 `sidebar.footer.action`
  插槽 + 宽屏布局 CSS，直接复用 v1.0.3 的产物与经验）
- 端点**完全对齐小程序现有 `utils/pair.js`**：`/pair/claim-wechat {code, jsCode}`、
  `/pair/verify-wechat {jsCode}`、二维码载荷 `{code, host, port, funnelUrl?}` —— 小程序零改动
- 安全基线照搬 v1.0.3 gate：每 IP 限速（120/分，认领 10/分）、`timingSafeEqual`、
  状态文件 0600 + icacls、CORS 仅 `http://127.0.0.1:3080`
- 配置：`~/.dsh/gate-wechat.json` `{appid, secret}`（0600）；**未配置时自动降级为
  开发态身份**（jsCode 的确定性哈希作为 dev openid），功能全通、可后续补配
- 状态文件独立命名（如 `~/.dsh/gate-wechat-state.json`），与 iOS 插件互不干扰

### 4.2 扫码配对：两个方案

**方案 A（主路径，v1 就上）**：打开小程序 →（未配置时）初始化页教安装 → 点「扫码配对」
→ `wx.scanCode` 读电脑端插件显示的二维码 → 小程序带 jsCode 调 claim → 绑定完成。
零微信 API 配额、个人主体可用、无需发布、开发期即可真机验证。✅

**方案 B（扫一扫直达，发布后可选增强）**：PC 端插件从微信 API 拉取一张
`getUnlimited` 小程序码（scene=配对码），用户用微信「扫一扫」直接扫码 → 自动打开小程序
并带上配对码 → 小程序静默 wx.login + claim。要求：小程序已发布、PC 可联网、appid/secret
已配置。配对页同时保留「手动输入配对码」兜底。✅ 列为 v2。

### 4.3 公网预留（暂不暴露）

二维码载荷与小程序配置保留 `funnelUrl` 字段 + `ENABLE_FUNNEL` 开关；README 写清楚
发布版真机必须 HTTPS+备案域名反代。本插件不做任何公网暴露动作。

## 5. 待决策点（历史提案 —— 已全部拍板，见 §5b）

1. **端口与共存**：默认沿用 3090/3091（小程序零改动、与旧 gate 协议无缝替换）；
   若要和 iOS 插件同时安装，两插件需错开端口（env 覆盖）。倾向：默认 3090/3091。
2. **方案 B（扫一扫直达）**：列 v2 发布后再做？还是 v1 就要？
3. **凭证滚动**：verify 成功后是否轮换 token（每次启动换新）？倾向：是。
4. **命名**：包名 `@harness-remote/dsh-wechat-remote`、仓库 `martinbear1/dsh-wechat-remote`，
   可改。
5. **旧 iOS 插件不动**：两个仓库独立演进，确认？

## 5b. 已拍板（2026-08-18）

1. **错开端口**：微信版默认 **3092（公网门）/ 3093（本地门）**，与 iOS 插件
   3090/3091 完全共存；env 覆盖 `WECHAT_GATE_PORT` / `WECHAT_GATE_LOCAL_PORT`。
2. **方案 B（扫一扫直达）**：同意列 **v2**（小程序发布后做，PC 端拉取
   getUnlimited 小程序码）。
3. **凭证滚动**：**要**。verify 成功即轮换 token；开发态（未配置
   gate-wechat.json）保持 `{valid: true, dev: true}` 不轮换。
4. **命名**：包名 `@harness-remote/dsh-wechat-remote`、仓库
   `martinbear1/dsh-wechat-remote` ✓。
5. **两插件独立互不影响** ✓；Web UI 侧边栏按钮显示为「**微信连接**」；
   小程序端代码由小程序侧开发者自行修改，插件侧只提供适配清单。
