## 1. 为什么修改

### 中文 Node 路径：已复现的安装器缺陷

旧版把 Node 中文绝对路径直接写入 UTF-8 批处理。后台 cmd 使用其他代码页时会读错路径，出现“系统找不到指定的路径 / pnpm failed”。外层手动 chcp 不能可靠控制所有后台子进程。

新版批处理只含 ASCII，通过 Windows 原生 Unicode 环境变量传递 Node 和 pnpm 路径，并关闭延迟变量展开。没有要求用户重装 Node、迁移目录、改变系统语言或放宽 PowerShell 执行策略。针对中文、空格、`!%&()`、936/65001 的实际子进程测试通过；儿童 Windows 在真实中文加空格 Node 路径完成安装、更新、自动重启和回退。

PowerShell 拒绝 npx.ps1 是另一个独立问题，发生在安装器启动前。文档推荐 Windows 使用 `npx.cmd`，不自动修改系统执行策略。

### 原目录原生安装：删除搬迁造成的问题

旧版复制整个 profile 到更深的 staging-home 安装，再搬回去，会改变相对本地依赖的含义，并留下 pnpm 的旧目录记录。此前用来源限制绕开问题，反而排除了原生可用的安装环境。

新版调用目标 DSH 的官方 `plugin --profile <名称> add`，在原 profile 内完成依赖解析和插件注册；不直接改写 DSH 本体，不手工拼装依赖树。删除 staging-home、来源白名单、其他插件逐包哈希准入、packageManager 强制重写。其他插件的 Git/file/link 来源本身不是拒绝理由。

备份只复制本次会改变的 profile，不再复制整个 DSH 数据目录；备份不运行，失败时恢复原位置，链接保留原含义。配对和会话留在原位置。Windows 目录联接及 POSIX 相对链接均有回归测试。

**明确代价：**原生安装发生在 DSH 停止后，更新离线时间包含依赖安装；不会承诺“安装全程在线”。避免目录搬迁错误优先于表面上更短的停机时间。

### 已安装用户的旧记录：有针对性地恢复

儿童 Windows 从原版 1.7.6 升级时，真实出现 `ERR_PNPM_UNEXPECTED_VIRTUAL_STORE`，验证了旧 staging 记录确会影响后续安装。

新版仅在 pnpm 明确报告目录布局不匹配时，调用官方 `dsh plugin install` 重建原有布局，再 add 一次；不使用 --force、不删除锁文件、不改其他插件来源、不自动准许第三方构建脚本、不对任意网络错误无限重试。该真实升级复测通过，原会话及节点身份校验通过。

这不能反推所有旧用户都已受损。已经安装成功且正常运行的用户无需清空或重新配对。

## 2. 安装目标、重启与异常处理

- DSH 已运行：由受本机凭证保护的原生安装握手确认实际实例、CLI、home、profile 和 PID。NPX 正在运行时不会被 PATH 上的全局版本覆盖。
- DSH 未运行：按当前终端默认 PATH、npm 全局、项目/源码、唯一 NPX 缓存选择；找到普通默认入口就不枚举庞大旧缓存。只有“没有默认入口且存在多个缓存目标”才要求明确目标。
- 停止状态直接使用官方安装命令，不要求其他插件先成功启动；安装完成后尝试启动 DSH。文案区分“已安装/已启动”和“页面已验证就绪”，不把进程刚创建当成完整健康证明。
- 重启保留实际 DSH CLI、参数、账号及数据目录，不另装另启其他版本。不以 CPU/DSH 未登记为拒绝条件；端口归属、路径范围、包完整性、运行中任务和进程归属检查保留。
- 每次安装固定自己的 pnpm 工具副本，防止升级时删掉正在使用的工具。
- 同版本但运行被旧验证状态卡住时，普通安装命令会尝试修复，不只输出“无需更新”。Mac 已真实复现 HTTP 503 后恢复。显式 `--repair` 仍保留；不保证能自动修复任意宿主损坏。
- 尚未运行且包内版本号已相同时，不会仅凭版本号对全部文件做完整诊断；存在文件损坏时仍可显式 --repair。归属不明的多用户/特殊托管服务、已损坏到无法握手的运行实例，不能承诺无人干预更新。
- 错误输出包含原生退出码/信号及日志位置。超时先结束自己启动的安装进程树；无法确认退出时保留锁和诊断，不在后台仍写文件时强行回退。
- 第一次安装失败时，原 DSH 没有插件，不能依赖插件接口验证恢复。新增小型恢复适配器复用现有官方 profile/HMR 接口，仅在该异常路径加载；不常驻、不新增轮询。真实故障测试发现其打包缺少 CommonJS 内置模块桥接，修复后复测通过。

对第三方插件：不主动扫描其所有功能、不因未经验证而阻止安装、不擅自删除它。原生包管理器无法解析其实际坏依赖时仍可能失败；不能保证修复任意外部插件。运行中的 DSH 若已被其他插件破坏到无法握手，可先正常退出 DSH 后使用停止状态原生安装路径。

测试方式和局限：

1. WebUI 流程调用真实按钮后端接口，执行真实安装、校验、退出、重启和回退；未逐台录制人工点击浏览器按钮。为避免未发布候选误走线上，只替换精确制品下载位置和私人目录，不替换安装/校验逻辑。
2. 前向及坏包使用测试用 1.7.8-test.1/2 版本区分更新方向，完成后恢复未改动的 1.7.7。不能写成“公网 1.7.7 已发布并下载验证”。
3. 旧 1.7.6 的 WebUI 在第一次升级前仍执行旧更新器，无法由尚未安装的 1.7.7 追溯修复。受中文路径等旧缺陷影响者应使用新版 npm 命令过渡一次；本轮重点验证该路径以及安装新版后的 WebUI 更新。
4. ARM 第一轮测试夹具在切换启动环境前创建空会话，随后测试代码直接终止 DSH，异步初始保存发生竞态。事务的 before-hashes 证明升级前不存在该会话文件，不能记为更新丢会话。调整为切换环境后创建并检查会话，再执行原生更新；已验证会话保留。
5. 本次清理后未配置真实模型 API Key、未用手机完成新的扫码配对，也未验证所有 DSH/Node/CPU/后台管理器组合。升级保留已有身份/会话的测试与清理后重新配对是两回事。
6. Windows 额外 NPX 轮的测试清场脚本最初只匹配带引号的 CLI，未处理 npm `.bin/..` 和直接重启后的不带引号参数。产品两段更新已成功，但测试脚本恢复真实候选的校验退出；修正测试脚本为真实文件路径比对，再单独还原候选并复核。该脚本位于私有测试制品目录，不在产品包中；原始结果保留该清场记录，不把它隐藏成全流程零问题。

## 4. 三端与性能影响

最终插件包与正式 1.7.6 逐文件比较，运行代码仅以下五个模块变化：install-control、install-profile、install-runtime、update-service、update-worker；另有版本、类型声明和用户说明。聊天、附件、文件、通知、配对、加密、公网通道和 UI 业务文件字节未变，依赖清单未新增运行依赖。

新增工作发生在用户安装/更新/恢复期间，不给正常会话增加后台扫描、定时器或新常驻服务。首次失败恢复器的生成包较大主要来自复用 YAML 解析器打包，不是新增数千行手写安装流程；实际源文件 44 行。

本次没有修改/上传小程序，没有改云端代码/账号/数据库/配置，没有部署重启生产服务。正式发布后如需让旧插件 WebUI 或小程序发现 1.7.7，只需按已有发布流程热更新云端外置更新目录；本轮未执行。不能以“业务代码未变”承诺绝无未知回归，但现有回归与真实环境检查未发现新的业务影响。
