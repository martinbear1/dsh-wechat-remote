## 两个根因及修复

1. 公网二维码一直携带 `relay`，但小程序从 `d8507e27b087e6d3d80aa17930cf2ca5559e6e57` 开始先检查可恢复 LAN 路由，读取 `relayOrigin`。带 LAN 信息的公网码在微信登录之前即抛出“公网中继地址无效”。修复由 `publicPairingPayload()` 统一生成完整 QR v1，从同一状态提供两个兼容字段，保留原字段、节点 ID、二维码公钥、票据和 LAN 信息。不绕过 HTTPS、账号所有权或公钥校验。
2. 修复字段后，用真实云端 HTTP 路由测试第二台设备，发现已消费但尚未过期的单次票据被 `ensurePairingTicket()` 缓存复用。改为生成/刷新二维码时经 `PublicRelayGateway.ensurePairingStatus()` 强制签名申请新票据；普通状态读取不刷新，并发请求复用同一次申请。正常换机不会轮换私钥或新增节点，既有撤销身份处理保持不变。

配套处理：旧独立 `/pair` 页面原本每 25 秒自动刷新，新票据会令旧票据失效。移除定时刷新，提供明确的“重新生成二维码”按钮，按实际有效期显示提示；QR HTML 和 JSON 均禁止缓存。WebUI 日常状态轮询只读取 `/gate/status`，不会反复换票据。

## 后续换机自动恢复

插件具备稳定节点 ID/公钥和签名身份，云端按微信账号保存并可查询已有节点；这次确保手动重新扫码可以复用原身份。未新增与手机绑定的第二套节点身份或字段。

免扫码自动恢复仍需小程序完成：登录后发现已有节点、和本地节点幂等合并、恢复可信的端到端身份校验、处理多账号与撤销状态。尤其不能把云端返回的公钥无条件当成用户曾扫码确认过的公钥；应先明确可信恢复方案，再判断是否需要插件/云端的附加证明接口。现在不能承诺“以后只改小程序就一定足够”。
