# 插件维护待办

本文件只记录维护者后续升级时需要处理的内部事项，不属于用户安装或使用说明。

## P1：公网 Agent WebSocket 半开后本地假在线，无法自动恢复

- 状态：已确认故障机制，尚未修复
- 首次确认：2026-08-30
- 已观察版本：`1.6.0-rc.3`
- 同类代码存在于：`1.5.5`
- 建议处理时机：下一次插件端升级；先进入下一个 RC，再回移到稳定版
- 修复范围：插件端；不应要求更新小程序，也不需要改变现有公网协议

### 用户症状

- 小程序将原来可以使用的电脑节点显示为“离线”，反复重连仍不能恢复。
- 电脑插件的本地状态仍显示公网 `online`。
- 重启 DSH 后，同一节点身份立即恢复，小程序重新显示在线。

### 2026-08-30 现场证据

- Windows DSH `0.1.2-alpha.1`、插件 `1.6.0-rc.3` 进程及本地端口正常。
- 本地 `host.describe` 与插件隔离接口 `wechatHost/describe` 均成功，排除 DSH API 兼容失败。
- 本地 `/gate/status` 连续报告公网 `online`，但云端权威 `/v1/nodes` 对同一节点连续报告 `online: false`。
- 本地仍存在到正确中继服务器的 TCP/TLS 连接；本机与云端节点公钥指纹、TLS 证书指纹完全一致，未发现链路劫持或节点冒充证据。
- 插件没有重新发起 Agent WebSocket 上线；重启 DSH 后，本地与云端同时恢复 `online`，节点 ID 未变化。

### 已确认的问题层级

`PublicRelayAgent` 在 WebSocket `open` 后标记在线，但没有客户端主动存活探测或超时回收。网络、代理、NAT、休眠唤醒等因素若留下半开连接，并且客户端没有收到可靠的 `close`，插件会永久保留假在线状态，也不会进入现有的指数退避重连流程。

自然环境中第一次造成半开连接的具体网络事件尚未确定，但不影响修复该存活性缺口。新增 Linux 节点不是根因；新增节点触发了小程序重新读取云端权威在线状态，因此暴露了此前被本地假在线掩盖的问题。

### 计划修复

修改 `src/public-relay-agent.ts`，保持协议和 DSH 适配层不变：

1. WebSocket 建立后启动有代次隔离的心跳管理器。
2. 发送标准 WebSocket `ping`，收到 `pong` 时更新最后存活时间。
3. 连续超时后使用 `terminate()` 结束半开连接，使现有 `close -> scheduleReconnect()` 流程接管。
4. 只有收到云端 `relay.ready` 后才将 Agent 标记为 `online`；为该确认设置超时。
5. 在停止、关闭、重连和连接被替换时清理所有定时器；旧连接的回调不得影响新连接。
6. 本地状态应及时变为 `offline`/`connecting`，不得在云端已移除连接后长期显示 `online`。

心跳只使用 WebSocket 控制帧，不携带用户内容，不改变端到端加密、配对身份或 DSH API。

### 可重复的自动化验证

不依赖再次遇到真实网络故障。使用可控的假 WebSocket/集成代理稳定模拟：

1. 连接成功并收到 `relay.ready`，随后丢弃所有 `pong`，且故意不触发 `close`；断言插件在截止时间内 `terminate()` 并重新连接。
2. 持续返回 `pong`；断言连接不会被误杀。
3. 连接只触发 `open`、不发送 `relay.ready`；断言确认超时后重连，且从未对外报告 `online`。
4. 建立新连接后再触发旧连接的超时和回调；断言新连接不受影响。
5. 模拟一次或多次失败后恢复；断言沿用同一节点身份，并通过现有指数退避最终回到在线。
